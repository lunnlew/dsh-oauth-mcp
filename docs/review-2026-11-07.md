# 评审记录 · 2026-11-07

六个评审分别从协议、安全、客户端、架构、测试、文档六个方面查了 `dsh-oauth-mcp`。
这一份记录写三件事：查了什么、已经改了什么、剩下的按什么顺序改。

评审只读代码，没有改任何文件。评审期间发现的缺陷由本次改动逐条修复，每条都配了测试。

## 1. 评审怎么做的

| 方面 | 查了什么 | 主要文件 |
| --- | --- | --- |
| 协议 | OAuth 2.1 与 MCP 规范的逐条对照：发现、注册、授权请求、令牌交换、PKCE、resource 绑定、MCP 传输与会话 | `lib/oauth/**`、`lib/mcp/**` |
| 安全 | 回调接收器、state 与 PKCE、令牌存放、脱敏、远程内容进入 agent 上下文的方式 | `lib/callback/**`、`lib/store/**`、`lib/util/redact.js` |
| 客户端 | 浏览器那一半：两份副本的漂移、React 用法、宿主契约、无障碍、被拒绝的写入 | `client/**`、`locale/**` |
| 架构 | 模块划分、依赖方向、重复的数据、生成脚本、错误词汇表 | 全仓库 |
| 测试 | 用例真正证明了什么、哪些断言是空的、哪些分支没人跑、哪些地方会不稳定 | `test/**` |
| 文档 | 每条事实与代码是否一致、写法、同一件事写了几遍 | `README.md`、`docs/**`、`DESIGN.md`、`TASKS.md` |

评审过程中发现一个测试自身的问题：端到端用例里 `mcp.setScenario({ requireAuth: true })`
用的名字与 mock 读的名字不同（`require-auth`），所以「服务器要求 bearer 令牌」这个场景**从来没有真正打开过**。
也就是说，端到端用例证明不了插件确实把 `Authorization` 头发给了 MCP 服务器——而这正是插件存在的理由。
名字已改正，并且 mock 现在会对不认识的场景名直接报错，这类笔误不会再悄悄溜过去。

## 3. 剩下的，按建议顺序（这一轮处理后的状态）

### 3.1 需要产品决定（两条）—— 都已处理

**一、客户端 secret 没有入口。** 已处理。
面板新增 secret 输入框（密码类型），保存时写进插件自己的配置；授权时复制进凭据记录，配置里的那一份可以清掉。
不选「凭据服务里另起一条记录」，是因为浏览器够不到 `ctx.credentials`，面板只能写插件自己的配置。
测试：`test/unit/panel-save.test.js`、`test/unit/service.test.js`。
文档：`docs/usage.md` 2.2、2.7、11 节，`docs/vendors.md` 3.1。

**二、明文 HTTP 的服务器地址。** 已处理。
不硬拦：地址是 `http://` 且不是回环时，字段下面给一条提示，HTTP 本身照常支持。
测试：`test/unit/panel-save.test.js`。

### 3.2 规范上还没做到的（两条）—— 都已处理

**三、`WWW-Authenticate` 里的 `resource_metadata` 只解析不用。** 已处理。
`lib/oauth/discovery.js` 新增 `challengeMetadataUrl()`：给 MCP 端点发一次不带令牌的请求，从 401 的 `WWW-Authenticate` 里取元数据地址；取不到再退回猜 well-known 路径。
测试：`test/unit/discovery.test.js`。

**四、受保护资源元数据的 `resource` 没有校验。** 已处理。
`resourceMatches()` 按 RFC 9728 §3.3 比对；不一致就拒绝这份元数据，缺 `resource` 字段则仍可用。
测试：`test/unit/discovery.test.js`。
实测：40 家里 39 家的探测仍然通（`pnpm run check:vendors`），Shopify 仍是边缘防护挡住的。

### 3.3 结构性（工作量最大）

**五、客户端那一份代码有两套手工副本。** 已处理。
面板、工具视图、命令卡、两者共用的助手，现在都由 `scripts/sync-client.mjs` 从
`client/panel.js`、`client/toolview.js`、`client/commandview.js` 生成到 `client/index.js`，
副本与来源逐行比对由 `test/unit/client-sync.test.js` 把关。
`pnpm run build` 一次跑完三个生成器，且是幂等的。

**六、授权超时与取消没有测试，取消也没有入口。** 已处理。
- 超时后 state 被丢弃、待处理请求被作者器忘掉，迟到的回调换不到令牌；
- 同一台服务器的第二次授权被拒绝（错误码 `authorization_in_flight`）；
- 新增 `/oauth-mcp cancel <serverId>`，取消进行中的授权；
- 新增 `test/unit/service.test.js`（7 个用例）。

**七、错误词汇表有三套。** 已处理。
三套代码现在都在一张表 `ERROR_CODES` 里，并分成三个命名的组：
`PLUGIN_CODES`（插件自己的失败）、`OAUTH_SERVER_CODES`（授权服务器返回的 OAuth 码）、
`CALLBACK_CODES`（回调接收端自己抛的码）。
三组不重叠，每个码都有一条 `error.<code>` 句子和一条 `error.<code>.next` 建议——
补齐的 23 条建议让回调页对任何码都能给出下一步。
`test/unit/errors-messages.test.js` 盯着这张表。

**八、同一件事写了几遍。** 已处理。
- 版本号：收进 `lib/build-info.js` 的 `PLUGIN_VERSION`（`index.js`、`lib/oauth/discovery.js`、
  `lib/mcp/session.js`、`lib/oauth/types.js` 都从那里读）；
- 服务器 id 的正则：收进 `lib/util/server-id.js`，配置 schema、服务器列表和提示文案共用；
- 生成脚本：有了 `pnpm run build` 这一个入口，三条生成命令都在里面；
- 厂商数量：`test/unit/vendor-count.test.js` 核对 README 与 usage 指南里写的数字，
  `TASKS.md` 里过时的「17 家」去掉；
- 厂商说明：英文 `notes`（给运维看的整段）与中文 `note`（表格里的一格）
  现在就在厂商表条目里紧挨着，不再分散在两处。

## 4. 这轮评审没能证明的

- 真实账号下的同意流程、授予的权限范围、工具的实际行为，一次都没有跑过。
  插件这一侧（请求的形状、回调的接收、厂商原话转达）验证过，账号那一侧没有。
- 厂商表是 2026-11-07 的实测元数据。Shopify 从这个地址被边缘防护挡住了，
  Figma 的动态注册在这个网络返回 403，两家没有完整复验。
  （2026-11-08 再跑一次 `pnpm run check:vendors`，40 家全通，Shopify 那次也通了；
  但被挡过一次的事实不变，两家的完整流程仍没有在真实账号上跑过。）
  （2026-11-09 补测 Todoist 并入表，现共 41 家；再跑一次 `pnpm run check:vendors`，
  40 家全通，Shopify 这次又被边缘防护挡住 —— 那条 403 说的是"你的客户端没有权限
  从这个 IP 取这个 URL"，是这个网络出口的问题，不是厂商改了元数据。
  Todoist 侧验到动态注册与授权请求都被接受，但同样没有真实账号的同意流程。）
- 主机那边的行为（配置服务、凭据服务、槽位注册）用的是假宿主。
  真宿主上的接口形状如果与假宿主不同，这里看不出来。
